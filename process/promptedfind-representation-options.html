Prompted Find — how to represent it

Two decisions, taken separately. Part 1 — story architecture: is Prompted Find a standalone project, or one surface of a named method (Semantic Decomposition)? Part 2 — the Interaction section: what replaces the current broken screenshot stepper? Each option is shown in the context it would actually appear in, with trade-offs, so a direction can be picked before any code changes.

Part 1 · Story architecture

The audience is recruiters, hiring managers, and practitioners skimming. The question: does naming the method upgrade the story ("she has a repeatable interaction primitive") without burying the artifact they actually want to see first?

Option A · Standalone, as today

Prompted Find stays a self-contained case study. Semantic Decomposition is never named; the existing “why this pattern matters beyond video” note carries the generalization. Fix the page, change nothing structural.

Option B · Method + application

Prompted Find remains an individual project page — but it opens by naming the method. Semantic Decomposition = break long-form content into labeled, navigable semantic units. Prompted Find = that method applied to video (“ask a question, get a location”). A compact “One pattern, three surfaces” strip inside the page points at the sibling surfaces (prose → view-spec lanes, research → Trails) as the family grows. No new page needed yet.

Against

  • The method lives inside one project page — someone landing on Trails first won’t see it (mitigated by repeating the tag line on siblings)
  • “Three surfaces” strip shows unshipped work; must be honest about status

Option C · Umbrella page

A dedicated Semantic Decomposition page becomes the parent: defines the method, then chapters for each surface. Prompted Find shrinks to a chapter (or keeps a thin page that redirects up). The homepage lists the umbrella as one large entry.

Working recommendation

Option B now, Option C later if earned. Keep Prompted Find as the individual, artifact-first project page; name Semantic Decomposition inside it as the method it applies. When a second surface genuinely ships (view-spec on prose, or Trails), extract the umbrella page and let each project link up to it. That way the story upgrade lands today without building a page around unshipped work.

Part 2 · The Interaction section

Current problems: the three screenshots don’t match the step captions (step 1 “open the panel” already shows segments; step 2 “segments appear” already shows the AI summary), the SVG spotlight coordinates are hardcoded against a 1280×614 image that gets cropped by object-fit:cover into a 16:8 box so the highlight drifts off-target, tab text is 10–11px, and step-04.jpg is shipped but never used. Three ways to rebuild it:

Option 1 · Repair the static stepper

Keep the format. Re-capture one screenshot per step that actually shows that step, fix the aspect ratio so nothing crops, align the spotlights, raise tab type to readable sizes. Smallest possible change.

For

  • A few hours of work; no deploy dependencies, no iframe weight
  • Works on mobile and in screenshots/OG previews exactly as designed

Against

  • Still static — a navigation pattern demonstrated without navigation
  • Undersells that a working 2,400-line prototype exists one click away

Option 2 · Live prototype + guided tour (Session Indicator pattern)

Do what session-indicator.html does: the repo becomes the demo. Deploy the PromptedFind repo to GitHub Pages with a slim video (the repo currently carries a 725 MB source MP4 — needs a compressed cut or the existing 84 MB webm trimmed further), embed it on the case-study page in a device frame, and drive a 3-step guided tour (driver.js, already proven in the Session Indicator repo) over the real UI: opens the Ask panel, highlights the segments, clicks one and seeks. The static stepper becomes the reduced-motion / mobile fallback.

For

  • The claim is the proof — “ask a question, get a location” happens in front of the reviewer
  • Reuses an already-proven pattern and codebase from Session Indicator (driver.js tour, Pages deploy, CNAME)
  • Turns the GitHub link from “trust me” into “touch it”; strongest possible signal for design-engineer roles

Against

  • Requires repo cleanup first: strip the 725 MB video, produce a ~10–20 MB cut, deploy to Pages
  • Iframe on a case-study page costs load weight; needs lazy-load and a poster state
  • Most work of the three options

Option 3 · In-page mini demo (Video Tape pattern)

Middle path, borrowed from the “Video Tape” decomposition page: no iframe — rebuild just the semantic timeline component natively on the case-study page, wired to the hero video that is already there. Labeled lanes under the video; click a segment, the hero seeks; the playhead tracks. The Ask panel is shown as stills; the timeline is real.

In context · under the hero video · live lanes, playhead at 2:58

Clicking a lane segment seeks the hero video above it; the red playhead follows playback.

For

  • Interactive proof without iframe weight or a repo deploy — all data is a small JSON of ranges
  • The component is the thesis: the decomposition itself becomes the interface on the page
  • Reusable: the same lane component later demos view-spec and the umbrella page

Against

  • Only demonstrates half the loop — navigation yes, the “ask a question” half stays static
  • A second bespoke component to maintain alongside the real prototype

Working recommendation

Option 3 as the near-term fix, Option 2 as the destination. The lane component under the hero is achievable now, kills every current bug (mismatched frames, drifting spotlight, 10px type), and directly visualizes Semantic Decomposition — which also serves Part 1 Option B. Then, when the PromptedFind repo is slimmed and deployed, add the live tour embed and keep the lanes as the summary view. Option 1 alone spends effort on a format that still can’t demonstrate the pattern.
